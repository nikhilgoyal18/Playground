### Claude Code's Limits Are Generous. The Problem Is Your Setup. `AI/ML`
- Claude Code Max 20x plan at €180/mo replaced API spend of €1,184.95/mo (~$1,389) for the same 8hr/day workflow — an 85% cost reduction, with no model swap or skipped sessions
- Anthropic shipped 3 bug fixes (v2.1.116+) between March 23–April 23 after users burned weekly quotas in 1–2 days; limits were reset for all subscribers; full postmortem published April 23
- **Cache miss math:** read = 0.1× input price; write (5-min TTL) = 1.25×; write (1-hour TTL) = 2×; cache hits reset TTL at no extra cost — long sessions stay warm indefinitely as long as the prefix doesn't change
- **Two rules that move the needle most:** (1) never add/remove MCP servers or tools mid-session — invalidates the cached prefix and forces full re-read; (2) never switch models mid-session — same reason; ~90% hit rate is healthy on 5-min default; 97–99% on 1-hour TTL (API-only, not available on Pro/Max/Team)
- **Context bloat fix:** Set `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=80` — drops context from 1M (expensive default for Opus 4.7) to 200K and triggers auto-compact at 80% instead of waiting for overflow; manually run `/compact` at 50% usage, `/clear` between unrelated tasks, `/rewind` when a turn goes sideways
- **Subagent model selection framework:** Haiku for bulk mechanical work (no judgment), Sonnet for scoped research and code exploration, Opus only for subtasks requiring real planning or tradeoffs; if a subagent needs a higher tier, it should return to the parent rather than escalate itself
- Skills can be promoted to subagent context by adding `agent: true` and `model:` to frontmatter — the parent gets back a short summary without the full content ever touching parent context (demonstrated with a `tldr-pdf` skill returning 5 bullets + 3 quotes from a PDF)
- **Wrong input format** is the fourth root cause of limit overruns — loading full files into context when only excerpts are needed, or not using tool calls to read incrementally; load lean by disabling unused MCP servers, tools, and plugins at session start

## ByteByteGo

### How Amazon Uses LLMs to Recommend Products `AI/ML`
- Amazon's core problem: "shoes for pregnant women" should surface slip-resistant shoes, but zero keyword overlap exists between query and product — traditional systems match text-to-text and can't bridge the semantic gap without human commonsense reasoning
- Existing solutions fell short: Alibaba's AliCoCo (163K nodes, 91 relations) and AliCG (5M nodes) focus on product attributes, not user intent; ConceptNet (8M nodes, 21M edges) covers general commonsense but has no e-commerce grounding; Amazon's own FolkScope covered only 2 product categories
- Amazon built **COSMO** — a commonsense knowledge graph — by feeding 3.14M co-purchase pairs and 1.87M query-purchase pairs across 18 product categories into **OPT-175B and OPT-30B** (not GPT-4; data privacy required internal infrastructure on 16 A100 GPUs)
- LLM output quality was low without filtering: only **35% of search-buy explanations** met Amazon's quality bar for typicality; co-purchase explanations were worse at **9%** — the rest were circular rationales like "customers bought them together because they like them"
- Sampling was intentional: co-purchase pairs were cross-checked to remove random co-occurrences; query-purchase pairs filtered by purchase rate and click rate thresholds; an in-house **query specificity service** prioritized broad/ambiguous queries where the semantic gap is largest
- Prompt design was formatted as question-answering tasks (not text continuation) with numbered candidate lists rather than single responses — structured output improved reasoning quality over naive prompting
- The architectural insight: commonsense knowledge graphs (why people buy) are distinct from factual product KGs (what products are) — and that gap is where LLM-extracted knowledge adds unique value that neither retrieval nor keyword search can replicate

## Nathan Baugh — World Builders
*1 issue this period*

### Depth Over Breadth as the Core Editing Discipline `Other`
- Core principle: "Fewer ideas, but better" — the failure mode is not bad ideas 3–7, but that they consume time and space from ideas 1–2, diluting total impact
- Two reader failure modes from idea overload: (1) confusion from bouncing between too many ideas too quickly, (2) boredom from insufficient depth on the best ideas — both destroy engagement
- **Diagnostic exercise:** divide a journal into categories (Plot, Characters, Themes, Scenes) and list everything in the section you're worried about — visual crowding becomes immediately apparent and confirms what instinct already knew
- Scrapping one idea mathematically increases the percentage of the remaining pie taken by stronger ideas — compounding effect: removal raises signal density, then deeper development amplifies it further
- Which parts do you struggle to write or return to? Baugh frames this as the story communicating where not to focus — the instinct that something isn't working is data, not insecurity
- Applies beyond fiction: essays, product specs, pitch decks — any document with competing claims of attention follows the same logic; the principle is framework-agnostic
