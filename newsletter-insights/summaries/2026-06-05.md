### How OpenAI Built Its Data Agent `AI/ML`
- OpenAI's data platform scale: 1.5 exabytes across 90,000 datasets, ~4,000 internal users as of May 2026; core bottleneck was never writing SQL — it was **finding the right tables and understanding their semantic meaning** (many tables look similar but mean different things; grain, join logic, and intent all vary)
- Solution: a "pretty vanilla" agent — described by the team itself as standard architecture — with **6 layers of context** that turn a single LLM into a reliable analyst across 90,000 tables; the insight is that strong data infrastructure foundations make simple agent architecture sufficient
- Question → verified answer in 3 steps; reliability comes from the context layers (table metadata, lineage, usage patterns, semantic descriptions), not from model complexity
- Codex use cases inside OpenAI: (1) migrated 10,000 DAGs, 90,000 tables, and 600 petabytes between clouds in 2 months — a task that would normally take years; (2) hands-off open-source dependency patching; (3) automated support triage
- Key lesson: "the hardest part of data analysis isn't writing SQL" — applies to any enterprise AI agent; solving the retrieval and semantic disambiguation problem at the infrastructure layer unlocks disproportionate agent capability
- For teams building domain agents: invest in the metadata and context layer first; a simple agent on top of rich context outperforms a sophisticated agent on top of sparse context

### The Path of a Request: A Tour of Modern Web Architecture `Engineering`
- A single web page load involves ~10 distinct systems in under a second; the architecture is a **funnel**: each layer absorbs as much traffic as it can before passing the rest along, so most requests never reach the database
- Framework for evaluating each layer: two questions — what is this layer doing, and what trade-off is it making? Every layer adds latency while absorbing load; understanding the trade-off at each hop is how you diagnose performance issues and design systems correctly
- Layers include: DNS resolution, CDN, load balancer, reverse proxy, application server, cache, message queue, database — each with distinct performance characteristics and failure modes
- Practical relevance: developers who only understand the application server layer will misdiagnose performance problems and make wrong architectural decisions; the system view is essential for production reliability

### ChatGPT Is Building Your B2B Shortlist — Without You `Product`
- Buyer behavior shift: buyer opens ChatGPT, asks "which tool should I use for X," gets 3 names with reasons, talks to those 3 — **the shortlist is now built in a chat you never see**
- **69% of buyers picked a different vendor than they originally planned** because of what the AI recommended; a third bought from a company they had never heard of before the chatbot named it
- The model never visits your homepage; it reads what everyone else has written — reviews, third-party comparisons, community posts — things you can't buy placement in; paid placement actively counts against you
- **Language is the invisible lever**: model matches a buyer's question to a product by vocabulary; if your product is written in internal jargon and the buyer thinks in everyday terms, the model moves on to whoever already wrote things up the way the buyer thinks
- A salesperson would hear the mismatch and translate in real time; the model has no reason to — it just skips you
- Fix: extract the exact phrases buyers use from support tickets and sales call transcripts; close the gap between how your team describes the product and how buyers describe the problem; this is the only distribution lever that works in an AI-mediated buying journey

## Productify (Bandan)

### AI Product Evaluation Framework — Five Task Types, Seven Metrics `AI/ML`
- Core problem: teams pick accuracy because it's easy to explain in a slide; wrong metric = months optimizing toward an outcome nobody actually wanted; "the metric you pick doesn't just measure quality — it defines what quality means"
- **The accuracy trap**: if 97% of transactions are legitimate, a model that labels everything "not fraud" scores 97% accuracy while catching zero actual fraud — the number looks great, the feature is useless
- **F1 score fixes the trap**: balances precision (when the model flags fraud, how often is it actually fraud?) and recall (of all real fraud cases, how many did the model catch?); worked example — 5 transactions, model catches 2 of 3 fraud cases + 1 false alarm → accuracy 60%, F1 = 0.67, and 0.67 is actually informative
- Five NLP task types each require different primary metrics: classification tasks → F1/precision/recall; generation tasks → BLEU/ROUGE for translation/summarization; semantic similarity → cosine similarity / embedding distance; QA/retrieval → exact match + MRR; open-ended generation → human eval or LLM judge
- Rule of thumb: if your model's failure mode is *missing* real events (fraud, cancer, churn), optimize for recall; if failure mode is *false alarms* (spam filters, moderation), optimize for precision; F1 balances both when both matter equally
- For AI PMs: before finalizing any model evaluation plan, write down the failure mode that would hurt most — the metric should make that failure mode visible, not hide it behind a high average score
